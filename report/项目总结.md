## 1. 项目概述

CampusEvent 是一个校园活动报名与管理系统：管理员发布活动并审批报名，学生浏览活动、报名或取消，结果通过站内消息通知。

项目按「先设计、后编码」的方式推进：先用 UML 完成领域建模与关键交互设计，写出设计模式决策报告，再指导 AI 按设计实现；初版通过验收后打 `baseline-v1` 标签，随后接收变更单 CR-01（候补队列），在分支上完成变更并全量回归，打 `change-v2` 标签。

## 2. 需求分析

初始需求来自指导书 §3.2 与附录 B，共 8 个功能模块：

| 编号 | 模块 | 关键约束 |
|---|---|---|
| P2-F01 | 活动管理 | 名称/类型/时间/地点/容量/报名方式；容量为正整数 |
| P2-F02 | 活动查看 | 支持按名称筛选；已删除活动不可见 |
| P2-F03 | 报名/取消 | 同一活动不得有两条有效报名 |
| P2-F04 | 报名策略 | 直接报名自动通过；审核型进入待审核 |
| P2-F05 | 审批 | 批准时**再次**检查名额 |
| P2-F06 | 状态管理 | 待审核/已通过/已拒绝/已取消 |
| P2-F07 | 站内通知 | 报名与审核结果写入消息列表 |
| P2-F08 | 统计 | 已通过数、待审核数、剩余名额 |

需求阶段把附录 B 的 7 条业务规则逐条转成**可测判定点**（如「名额统计只计已通过」「通知失败不得让报名静默消失」），并显式记录三处原文未定但实现必须选边的取舍：软删除（BR7）、通知失败不回滚（BR6）、名额检查归属服务层（D4）。

## 3. 设计

### 3.1 分层与职责

```
Web（路由/鉴权/错误映射）
  → Service（用例编排 + 公共规则）
    → { Domain 实体, Policy 策略, Notify 事件 }
      ← Repo（接口）/ SQLite（实现）
```

核心约束：领域层不依赖 HTTP 与 SQL；服务层只依赖仓储**接口**；策略只做决策、无副作用。

### 3.2 两个模式与一个原则

- **策略模式**：`RegistrationPolicy.decide(ctx)` 只回答「通过还是待审核」，`DirectApprovalPolicy` 与 `ManualReviewPolicy` 是两种实现，`PolicyFactory` 按活动配置选择。服务层主流程没有 `if 活动类型` 分支。
- **观察者**：报名/审批状态变化发布 `RegistrationEvent`，`InboxNotifier` 订阅并写站内信；通知失败只写 `notify_failures` 留痕，不回滚业务。
- **名额规则**：名额是活动聚合的不变量，集中在 `RegistrationService`，不放进策略——策略不查库、不持有聚合状态。

### 3.3 设计决策（摘要）

完整论证见 `docs/design-decisions.md`，六个决策点均记录了候选方案、代价与**失效信号**：

| 编号 | 决策 | 被否决的主要方案 |
|---|---|---|
| D1 | 报名规则用策略 | if-else、状态模式、模板方法 |
| D2 | 通知用事件总线 | 服务内直调、消息队列、数据库触发器 |
| D3 | 持久化用 Repository | 服务内直写 SQL、ORM |
| D4 | 名额检查放服务层 | 放策略、放实体 |
| D5 | 删除活动用软删除 | 硬删、拒绝删除 |
| D6 | 前端用 Vue3+Vite | 服务端渲染、纯 API |

## 4. 实现

### 4.1 后端

| 层 | 文件 | 职责 |
|---|---|---|
| 领域 | `domain/models.py` | 实体、状态枚举、`isOpen`/`isFull`/`canCancel` 等领域判定 |
| 策略 | `policy/base.py` | 策略接口、两种实现、工厂 |
| 通知 | `notify/events.py`、`inbox.py` | 事件、进程内总线、站内信订阅者 |
| 仓储 | `repo/ports.py`、`sqlite_repo.py`、`db.py` | 5 个端口接口 + SQLite 实现 + 建表/迁移/种子 |
| 服务 | `service/{auth,activity,registration,message}.py` | 用例编排、公共规则、鉴权 |
| Web | `web/server.py` | 路由、Bearer Token、错误码映射、静态托管 |

数据库用 6 张表；`registrations` 上建**部分唯一索引** `WHERE status IN ('PENDING','APPROVED','WAITLISTED')`，把「同一活动不得重复有效报名」下沉为数据库约束，业务层校验只是友好提示。

### 4.2 前端

Vue 3 + Vite（JavaScript），6 个视图：登录、活动列表、活动详情、我的报名、站内消息、管理端。`api.js` 统一封装 Bearer Token 与错误体；开发期由 Vite 代理 `/api` 到 8000，生产期由后端托管 `dist/`，实现单进程单端口部署。

为避免「状态藏在二级页面」，活动详情页直接回显**我的报名状态**（待审核 / 已通过 / 已拒绝 / 已取消 / 候补第 N 位），并按状态切换按钮：有效报名显示「取消报名 / 取消候补」，终态显示「可重新报名」。

管理员视角另有「报名名单」卡片：已通过（报名成功）、候补（按位次）、待审核三组，含姓名与学号，方便现场核对。

### 4.3 前端构建与部署形态

| 形态 | 验证结果 |
|---|---|
| 开发（Vite 5173） | 页面加载 `/@vite/client`；`/api/activities` 经代理返回真实数据 |
| 生产（后端 8000） | `/` 返回构建后 `index.html`；`/assets/*.js` 200 且 `Content-Type` 正确 |

## 6. 需求变更（CR-01 候补队列）

### 6.1 变更内容

热门活动名额秒光，学生无法参与。CR-01 要求：直接型活动满员后进入**候补队列**，已通过者取消时按位次自动补位并通知；候补上限可配（默认 0＝不开放）；审核型活动行为不变。

验收后追加 **CR-02**：管理端「待审核申请」增加「转候补」，管理员可把任意待审核申请排入候补（未配置上限时自动补成容量）；同时禁止管理员账号报名，避免自批自报。

### 6.2 影响分析与实现

变更前先提交影响分析（`docs/change-impact.md`），明确「候补是容量规则的延伸，不是第三种报名策略」，因此**策略层零改动**。

实际改动：

| 层 | 改动 |
|---|---|
| 数据库 | 加 2 列；SQLite 无法修改 CHECK，用事务**重建 `registrations` 表**并保留数据 |
| 领域 | 新增 `WAITLISTED`、`waitlist_position`、`is_waitlist_full`、统计 `waitlisted` |
| 服务 | 满员转候补、取消后按序补位、`registration.promoted` 事件 |
| Web | **零改动**（错误码与响应结构本就通用） |
| 前端 | 候补展示、取消候补、表单字段 |

迁移在**真实旧库**上验证：启动后自动补列、重建表、接口正常。

### 6.3 可维护性对照

| 指标 | 预测 | 实际 |
|---|---|---|
| 新增类 | 0 | **0** |
| 修改的核心业务类 | 2 | **3**（多 `activity.py`，用于字段校验与透传） |
| 修改文件（总数） | 9 | **32**（后端 8 / 前端 5 / 测试 5 / 文档 11 / 配置 3） |
| 代码改动 | — | **+492 / −35**（生产代码 +269 / −30） |
| 回归失败 | 0 | **0** |

**结论**：D4（规则集中）成立——名额与候补判定只改了 `registration.py` 一处；但估算低估了**字段面**改动，新增聚合字段仍会牵动创建/更新入口。策略与 Web 层零改动，说明模式确实把「会变的东西」隔离住了。

### 6.4 两次返工（如实记录）

1. `find_active` 仍只查 `PENDING/APPROVED`，与「候补也算有效报名」不一致，重复报名被数据库唯一索引拦下并抛 `IntegrityError`（不是友好的 409）。修正查询后通过。
2. 详情页「加入候补」按钮沿用 `activity.open` 判断，而满员时 `open=false`，按钮被禁用。改为 `open || hasWaitlist`。

## 7. 可维护性结论

- **修改面收敛**：CR-01 只触及 3 个核心业务文件、0 个新增类，接口层与策略层未动。
- **回归成本低**：41 个单测覆盖策略、名额、状态机、幂等与重启一致性，变更后一次全过。
- **代价真实存在**：分层带来约 +150 行接口与一个事件间接层；调试时需要追事件链。这些在决策报告里已提前记录。

## 8. 反思与改进

1. **「有效报名」应集中定义**：本次返工暴露出状态集合散落在 SQL、领域属性、测试三处。改进：定义 `ACTIVE_STATUSES` 单一常量，SQL 由参数生成。
2. **迁移要尽早验证**：SQLite 的 CHECK 约束无法修改，必须重建表。若在实现末期才发现，风险很高；本次先写了迁移脚本并在旧库上实测，才敢合并。
3. **演示默认值要贴合场景**：候补上限默认 0 符合变更单，但演示时容易忘填而误以为功能失效，应在表单加提示。
4. **AI 协作的边界**：AI 负责生成代码与测试，但设计决策、取舍与验收判定必须由人给出；`AI_DEV_LOG.md` 记录了 8 个阶段的意图、采纳/修改理由与返工，可作为过程证据。
