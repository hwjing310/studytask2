| 提出方 | 校园活动管理中心（模拟教师发布） |
| 提出日期 | 2026-11-19 |
| 优先级 | 高 |
| 预计工作量 | 0.5–1 人日 |

---

## 1. 背景

初版上线后，热门活动（如羽毛球社招新、编程马拉松）名额在开放后数分钟内被抢完。学生反馈「点进去就满了，只能等下次」，管理员反馈「有人取消后名额空着，没人知道可以再报」。

现有实现的行为是：名额满时直接返回错误 `CAPACITY_FULL`，取消报名后名额空出但**不会自动补位**。

## 2. 变更内容

### 2.1 新增「候补」状态

- 报名状态新增 `WAITLISTED`（候补）。
- 适用范围：**仅直接报名型活动**（`policy_type = DIRECT`）。审核型活动保持现有逻辑（待审核不占名额，批准时校验名额），不引入候补，以避免与审批流程冲突。

### 2.2 候补规则

| 编号 | 规则 |
|---|---|
| CR-R1 | 直接型活动名额已满时，学生报名不再报错，而是创建 `WAITLISTED` 报名，按**报名先后**分配候补序号（从 1 开始递增）。 |
| CR-R2 | 每个活动可配置候补上限 `waitlist_capacity`（整数 ≥ 0）。候补人数达到上限后，再报名返回错误 `WAITLIST_FULL`。 |
| CR-R3 | 当一条 `APPROVED` 报名被取消（或活动容量被调大产生空位）时，**候补序号最小的学生自动转为 `APPROVED`**，并获得「已补位」站内通知。 |
| CR-R4 | 候补学生可以主动取消自己的候补，状态变为 `CANCELLED`，不影响名额，也不影响其他人的候补顺序。 |
| CR-R5 | 名额统计新增「候补人数」；`approved` 与 `remaining` 的既有口径**不得改变**。 |
| CR-R6 | 同一学生对同一活动的有效报名定义扩展为：`PENDING` / `APPROVED` / `WAITLISTED` 三者之一存在即视为重复。 |

### 2.3 接口约定（向后兼容）

- `GET /api/activities` 与详情：新增字段 `waitlisted`、`waitlist_capacity`。
- `GET /api/activities/{id}/stats`：新增字段 `waitlisted`。
- 报名接口 `POST /api/activities/{id}/registrations`：
  - 成功进入候补时返回 **201**，响应体 `status = "WAITLISTED"`，并包含 `waitlist_position`；
  - 候补已满返回 **409**，`error.code = "WAITLIST_FULL"`。
- 原有字段一律保留，不重命名、不删除。

## 3. 验收标准

| 编号 | 场景 | 预期 |
|---|---|---|
| CR-AC1 | 直接型活动容量 1，学生 A 报名通过后，学生 B 报名 | B 返回 201，状态 `WAITLISTED`，`waitlist_position = 1` |
| CR-AC2 | 候补上限设为 1，B 已在候补，学生 C 再报名 | 返回 409，`WAITLIST_FULL`，不产生记录 |
| CR-AC3 | A 取消已通过报名 | B 自动变为 `APPROVED`，收到「已补位」通知；`approved` 与 `remaining` 正确 |
| CR-AC4 | B 取消自己的候补 | B 状态 `CANCELLED`，候补人数 −1，A 的通过状态不受影响 |
| CR-AC5 | 查询统计 | 返回 `waitlisted`；`approved` / `remaining` 与变更前口径一致 |
| CR-AC6 | 回归 | C1–C10、E1–E10 全部重新通过 |

## 4. 约束

1. 不引入任何第三方依赖（后端仍为 Python 标准库）。
2. 不改变审核型活动的既有行为。
3. 数据库需要兼容已有数据：迁移时旧记录 `waitlist_position` 为 `NULL`，不得报错。
4. 必须提交：变更影响分析、新增/回归测试结果、可维护性对照数据（新增类数、修改的核心业务类数、回归失败数、AI 交互轮次、修改总时长）。
