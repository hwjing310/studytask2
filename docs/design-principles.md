## 1. 职责划分（SRP）

| 类 | 单一职责 | 明确不做什么 |
|---|---|---|
| `Activity` | 活动自身的状态判断（是否可报名、是否已下架、是否满员） | 不查数据库、不发通知 |
| `Registration` | 一条报名记录的状态与合法转换 | 不判断活动容量 |
| `RegistrationService` | 编排一次报名/取消/审批的用例流程 + **公共规则**（名额、重复、时间） | 不决定「通过还是待审核」（交给策略），不写消息（交给订阅者） |
| `RegistrationPolicy` 及其实现 | 只回答「这次提交应进入哪个状态」 | 不查库、不做名额判断、不发通知 |
| `EventBus` | 事件的分发 | 不关心订阅者做什么 |
| `InboxNotifier` | 把领域事件翻译成站内消息 | 不改变报名状态 |
| `*Repository` | 持久化与查询 | 不含业务规则 |
| `*Handler` | HTTP 解析、鉴权、错误码映射 | 不含业务规则 |

> 反例（本项目明确避免）：把「查名额 + 判断类型 + 发消息 + 写库」全塞进一个 `register()` 方法。那样策略无从落地，变更时会同时改到 4 件事。

## 2. 开闭原则（OCP）

- 新增一种报名方式（例如「先到先得 + 候补」）= 新增一个 `RegistrationPolicy` 实现 + 在 `PolicyFactory` 注册一行；`RegistrationService` 不改。
- 新增一种通知渠道（站内信 → 邮件）= 新增一个 `EventSubscriber`；报名与审批代码不改。
- 反证：若用 `if (activity.policyType == "REVIEW")` 分支，则每加一种方式都要改核心方法，且这个方法的回归面覆盖全部用例。

## 3. 里氏替换（LSP）

`DirectApprovalPolicy` 与 `ManualReviewPolicy` 都满足契约：

- 输入相同（`RegistrationContext`：活动、学生、当前已通过数）；
- 输出只允许是 `APPROVED` 或 `PENDING`，不得返回 `CANCELLED`/`REJECTED`；
- 不得有副作用（不写库、不发消息）；
- 不得抛业务异常，容量与重复问题由服务层在调用前拦截。

因此 `RegistrationService` 在替换实现时无需任何条件判断。

## 4. 接口隔离（ISP）

| 接口 | 方法数 | 为什么拆开 |
|---|---|---|
| `ActivityRepository` | 6 | 活动服务与报名服务用的子集不同，但都围绕活动聚合，合并合理 |
| `RegistrationRepository` | 6 | 报名查询模式与活动差异大，单独一个接口避免污染 |
| `MessageRepository` | 3 | 仅通知与消息页使用 |
| `NotifyFailureRepository` | 1 | 只服务于 BR6 的留痕，单独接口让「通知失败」成为一个显式能力 |

> 没有做「一个大 Repository 接口装所有方法」——那会迫使每个实现类都实现用不到的方法。

## 5. 依赖倒置（DIP）

- 服务层依赖 `RegistrationPolicy`、`EventBus`、`*Repository` 等**抽象**；
- `SqliteRepositories` 在 `app.py` 组装时注入，业务代码不 `import sqlite3`；
- Web 层依赖服务层，不直接依赖仓储。

依赖方向：`Web → Service → {Domain, Policy, Notify} ← Repo 实现`。

## 6. 设计任务B：名额检查为什么是公共规则

**结论**：名额检查放在 `RegistrationService`，策略只决定状态。

理由：

1. **两类策略都需要**：直接型要知道「能不能通过」，审核型要知道「批准时还能不能通过」。若把名额判断放进策略，审核型在**提交时**就会误判（此时待审核不占名额），必须再写一遍「批准时检查」，造成规则重复。
2. **名额是活动的不变量**，不是某种报名方式的特性；把它放在策略里等于让策略承担聚合根的一致性职责。
3. **可测性**：容量相关的用例（C4、C8、E9）只针对服务层写一次即可覆盖两种模式。
4. **变更影响小**：若将来允许「超卖比例」或「候补队列」，只改服务层的一处规则，策略不受影响。

对应时序图：`seq-register-direct`（提交时检查）、`seq-approve`（批准时再检查）。

## 7. 设计任务C：通知解耦、失败与重复

**解耦方式**：观察者（`EventBus` + `EventSubscriber`），而非在 `RegistrationService` 里直接调消息表。

**事务边界（BR6）**：
1. 报名/审批在**同一数据库事务**内完成（业务事实先落库）；
2. 事务提交**之后**发布事件；
3. 订阅者写消息失败 → 捕获异常，写 `notify_failures(event_id, payload, error)`，**不回滚**报名；
4. 接口仍返回成功，前端提示「报名成功（通知可能延迟）」。

**为什么这样切**：报名是用户的核心诉求，通知是附属效果。若通知失败就回滚报名，用户会看到「明明点了却什么都没发生」，且消息服务抖动会放大成业务不可用。

**避免重复通知**：
- 每个事件带唯一 `event_id`（`registration_id + 目标状态 + 版本号`）；
- `messages` 表对 (`registration_id`, `status`) 建唯一索引，重复插入被数据库拦下；
- 订阅者按 `event_id` 幂等处理，重放不会产生第二条消息。
