## 1. 引言

### 1.1 目的
本文件定义 CampusEvent 初始版本的业务需求、数据需求与非功能需求，作为 UML 设计、编码、验收测试与第二周变更影响分析的唯一基线。

### 1.2 范围
校园管理员发布活动，学生浏览活动并报名。初始版本支持两类活动：**直接报名**（提交即通过）与**管理员审核**（提交后待审核）。报名与审核结果通过**站内消息**通知学生。

### 1.3 不在范围内
- 用户注册、找回密码、复杂权限体系（仅使用固定演示账号）。
- 邮件/短信/微信等外部通知渠道；消息队列。
- 支付、签到、活动评价、场地审批。
- 多租户、多校区隔离。

### 1.4 术语
| 术语 | 含义 |
|---|---|
| 活动 Activity | 可被报名的校园活动，含时间、地点、人数上限、报名方式 |
| 报名 Registration | 一名学生对一个活动的一次申请记录，带状态 |
| 有效报名 | 状态为「待审核」或「已通过」的报名 |
| 报名策略 RegistrationPolicy | 决定「提交后直接通过还是进入待审核」的规则对象 |
| 名额 capacity | 活动允许的「已通过」报名数量上限 |
| 站内消息 Message | 写入学生消息列表的通知记录 |

## 2. 总体描述

### 2.1 角色
| 角色 | 说明 | 主要操作 |
|---|---|---|
| Student 学生 | 使用固定演示账号（如 `s001/张同学`） | 浏览活动、报名、取消、看我的报名、看消息 |
| Admin 管理员 | 使用固定演示账号（如 `admin/管理员`） | 增删改活动、审批报名、看统计 |

> 账号为演示用固定账号，口令以哈希形式存库；不实现注册与角色管理界面。

### 2.2 运行环境
| 层 | 技术 | 说明 |
|---|---|---|
| 前端 | Vue 3 + Vite（JavaScript，非 TypeScript） | 单页应用；开发期 `npm run dev`，生产期构建为静态 `dist/` 由后端托管 |
| 后端 | Python 3.12 标准库（`http.server`） | 提供 JSON API 与静态文件服务；**不引入需 pip 安装的第三方库** |
| 数据 | SQLite 3（单文件） | 落盘 `project/data/campusevent.db` |
| 部署 | Linux 云主机（thevibehosting.com） | 后端常驻 + 静态资源托管；提供启动脚本与反向代理说明 |

### 2.3 设计约束
1. 后端零第三方依赖（离线可运行），领域层不得直接依赖 HTTP 或 SQL。
2. 报名规则必须通过**策略抽象**表达，主流程不得用活动类型 `if/else` 硬编码分支。
3. 通知必须与报名业务**解耦**（观察者或等价事件分发），不得在报名服务里直接写消息表。
4. 同一份代码需能同时服务：本地演示、自动化测试、云主机部署。

## 3. 功能需求

| 编号 | 模块 | 需求描述 |
|---|---|---|
| P2-F01 | 活动管理 | 管理员可创建、编辑、删除活动；字段含名称、类型、开始时间、地点、人数上限、报名方式（直接/审核）。创建时校验：名称非空、类型合法、时间合法、容量为正整数、报名方式为两种之一。 |
| P2-F02 | 活动查看 | 学生可浏览活动列表与详情，列表支持按名称关键字筛选；已删除活动不出现在列表与详情中；列表显示剩余名额。 |
| P2-F03 | 报名/取消 | 学生可对活动报名、取消自己的报名；同一活动不得出现两条有效报名。 |
| P2-F04 | 报名策略 | 直接报名活动：提交后自动通过；审核型活动：提交后进入待审核。策略由活动配置决定，运行期可选。 |
| P2-F05 | 审批操作 | 管理员可批准或拒绝待审核申请；**批准时必须再次检查剩余名额**，名额不足则批准失败且不改变状态。 |
| P2-F06 | 状态管理 | 报名状态限：待审核 `PENDING`、已通过 `APPROVED`、已拒绝 `REJECTED`、已取消 `CANCELLED`；状态转换必须符合 §7。 |
| P2-F07 | 站内通知 | 报名结果与审核结果写入学生站内消息列表；消息含活动、内容、时间、是否已读；学生可查看并标记已读。 |
| P2-F08 | 统计 | 管理员可按活动查看：已通过数、待审核数、剩余名额（= 容量 − 已通过数）。 |

### 3.1 接口约定（前后端）
统一前缀 `/api`，JSON 请求/响应，错误体 `{ "error": { "code": "...", "message": "..." } }`。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/login` | 演示账号登录，返回角色与身份 |
| GET | `/api/activities?q=` | 活动列表（含剩余名额） |
| GET | `/api/activities/{id}` | 活动详情 |
| POST | `/api/activities` | 管理员创建活动 |
| PUT | `/api/activities/{id}` | 管理员编辑活动 |
| DELETE | `/api/activities/{id}` | 管理员删除活动（软删除） |
| POST | `/api/activities/{id}/registrations` | 学生报名 |
| GET | `/api/registrations/mine` | 我的报名 |
| POST | `/api/registrations/{id}/cancel` | 取消报名 |
| GET | `/api/registrations/pending?activity_id=` | 管理员看待审核列表 |
| POST | `/api/registrations/{id}/approve` | 批准 |
| POST | `/api/registrations/{id}/reject` | 拒绝 |
| GET | `/api/messages` | 我的站内消息 |
| POST | `/api/messages/{id}/read` | 标记已读 |
| GET | `/api/activities/{id}/stats` | 活动统计 |

## 4. 业务规则

| 编号 | 规则（来自附录B.2） | 可测判定点 |
|---|---|---|
| BR1 | 直接报名活动：名额充足且符合基本条件时，创建「已通过」报名，并产生站内通知。 | 提交后状态为 `APPROVED`；消息表新增 1 条 |
| BR2 | 审核型活动：提交后为「待审核」，由管理员批准或拒绝；**批准时再次检查剩余名额**。 | 提交后 `PENDING`；批准时若已满则失败 |
| BR3 | 名额统计按「已通过」计算；待审核不占名额；满员后不得再批准新报名。 | 已通过数 = `APPROVED` 计数；满员后批准返回错误 |
| BR4 | 同一学生对同一活动不得存在两条「待审核」或「已通过」的有效报名；已取消/已拒绝记录保留，允许再次申请。 | 第二次提交返回冲突错误；取消后可再次提交成功 |
| BR5 | 学生可取消自己的「待审核」或「已通过」报名；**活动开始后不允许新增报名**。 | 取消后状态 `CANCELLED`；开始后报名被拒 |
| BR6 | 通知失败应留痕，但不得导致已合法提交的报名记录无声消失；事务边界由设计说明。 | 注入通知失败后：报名记录仍存在，失败有日志/记录 |
| BR7 | 活动与报名必须持久化；删除已有报名的活动时，采用「拒绝删除并提示」或「软删除」，需说明选择。 | 重启后数据一致；删除行为与所选方案一致 |

### 4.1 本项目的取舍声明（需在报告中论证）
- **BR7 选择「软删除」**：活动表增加 `deleted_at`；删除后列表与详情不可见、不可报名，历史报名与消息保留。理由：审计与历史一致性优先，避免级联删除破坏已发生的业务事实。
- **BR6 事务边界**：报名先提交（同库事务内写 `registrations`），提交后再发布领域事件；通知失败写 `notify_failures` 记录，不回滚报名。
- **名额检查归属**：名额属于**公共规则**，放在 `RegistrationService`（两种策略都要用）；策略只决定「通过」还是「待审核」。理由见设计模式决策报告。

## 5. 数据需求

| 实体 | 主要字段 | 约束 |
|---|---|---|
| Student | `student_id`、`name`、`password_hash` | `student_id` 唯一 |
| Activity | `activity_id`、`title`、`category`、`start_at`、`location`、`capacity`、`policy_type`、`deleted_at` | `capacity` 为正整数；`policy_type ∈ {DIRECT, REVIEW}`；开始前允许报名 |
| Registration | `registration_id`、`activity_id`、`student_id`、`status`、`created_at`、`updated_at` | 状态限四种；(`activity_id`,`student_id`) 上不得有两条有效报名（部分唯一索引） |
| Message | `message_id`、`student_id`、`activity_id`、`content`、`created_at`、`is_read` | 报名/审核动作可产生消息 |
| NotifyFailure | `id`、`event_id`、`payload`、`error`、`created_at` | 通知失败留痕（BR6） |

> 时间统一存 ISO-8601 字符串（UTC+8 语义），比较按字符串即可（ISO 格式字典序 = 时间序）。

## 6. 非功能需求

| 编号 | 类别 | 要求 | 验证方式 |
|---|---|---|---|
| NFR1 | 性能 | 数据量 ≤ 10⁴ 条时，95% 的 API 请求 < 300 ms | 脚本压测 200 次取分位 |
| NFR2 | 并发 | 10 并发报名同一活动不超卖（已通过数 ≤ 容量） | 并发脚本断言 |
| NFR3 | 可靠性 | 进程重启后活动、报名、消息一致，无丢失 | C10 用例 |
| NFR4 | 安全 | 口令哈希存储；全部 SQL 参数化；写操作校验身份与参数；不返回他人数据 | 代码审查 + 越权用例 |
| NFR5 | 可维护性 | 分层：domain / policy / notify / service / repo / web；核心业务类不依赖 HTTP、SQL | 依赖方向检查 |
| NFR6 | 可移植 | Windows 与 Linux 均可运行；前端构建产物可由后端直接托管 | 两环境启动验证 |
| NFR7 | 可观测 | 关键动作输出结构化日志（JSON Lines），含请求 ID | 日志抽样 |

## 7. 报名状态模型

> v1.1（CR-01 候补）在此基础上新增 `WAITLISTED`，详见 §10 与 `docs/uml/state-registration.md`。

```
            (直接型报名，未满)
  [*] ────────────────► APPROVED
            (直接型报名，已满且候补未满)
  [*] ────────────────► WAITLISTED ──有人取消自动补位──► APPROVED
        (审核型报名)
  [*] ────────────────► PENDING ──批准(名额足)──► APPROVED
                          │  └────拒绝──────────► REJECTED
                          └────学生取消─────────► CANCELLED
  APPROVED ────学生取消───► CANCELLED
  WAITLISTED ──学生取消───► CANCELLED
```

| 当前状态 | 事件 | 目标状态 | 附加条件 |
|---|---|---|---|
| — | 直接型活动报名 | APPROVED | 未开始；无名额不足；无有效报名 |
| — | 直接型活动报名（已满） | WAITLISTED | 未开始；无有效报名；候补上限 > 0 且未满 |
| — | 审核型活动报名 | PENDING | 未开始；无有效报名 |
| PENDING | 管理员批准 | APPROVED | 剩余名额 ≥ 1 |
| PENDING | 管理员拒绝 | REJECTED | — |
| PENDING | 学生取消 | CANCELLED | 本人操作 |
| WAITLISTED | 有人取消已通过报名 | APPROVED | 该学生为候补序列最小者 |
| WAITLISTED | 学生取消候补 | CANCELLED | 本人操作；不释放名额 |
| APPROVED | 学生取消 | CANCELLED | 本人操作；触发补位 |
| REJECTED / CANCELLED | — | 终态 | 可再次申请（新建记录） |

## 8. 假设与依赖
1. 单一部署实例，SQLite 单写入者；不追求分布式一致。
2. 服务器时间可信，活动时间以服务器时钟为准。
3. 演示账号固定，口令由初始化脚本写入。
4. 变更单（CR）由教师在 `baseline-v1` 验收后发布；本仓库不预置任何 CR 相关功能。
5. 云主机为 Linux + Python 3.8+（项目在 3.12 验证）。

## 9. 验收基线
初始版本以 `docs/test-cases.md` 的 C1–C10 为最低验收集；全部通过后打标签 `baseline-v1`。
