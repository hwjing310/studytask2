## 0. 这份文档回答什么

不是「我用了哪些设计模式」，而是六个具体决策点的论证：

> 在当时的约束下，有哪些候选方案？为什么选这个？付出什么代价？如果当初的假设不成立会怎样？

每条决策记录包含：背景 → 候选与对比 → 结论与理由 → 代价 → 被否决方案的理由 → **失效信号**（出现什么现象说明这个决策需要重审）。

## 1. 设计目标与约束

| 类型 | 内容 |
|---|---|
| 目标 | 需求可验收（C1–C10 全过）；报名规则与通知机制可独立演进；核心业务不依赖 HTTP/SQL |
| 约束 | 后端零第三方依赖（离线可跑）；2 周工期、1 人；SQLite 单机；界面用 Vue3+Vite |
| 评分导向 | 「学生主导的设计」30 分看职责划分与模式应用**理由**；「变更适应」30 分看**修改范围与可维护性证据** |

## 2. 决策记录

### D1 报名规则可变 → 采用策略模式

**背景**：初始有两种报名方式（直接通过 / 管理员审核），且指导书暗示后续可能新增（变更单）。
若用 `if (activity.policyType == "REVIEW")` 写在 `register()` 里，新增一种方式就要改核心方法。

**候选对比**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| if-else 分支 | 类最少、上手最快 | 每加一种方式都改核心方法；分支与名额/通知逻辑缠绕；回归面覆盖全部用例 | 否决 |
| 状态模式 | 能表达「待审核→通过/拒绝」流转 | 状态模式解决的是**对象状态驱动行为**；本项目的差异在「提交时如何判定」，不是状态迁移；用它会把简单判定包装成状态机 | 否决 |
| 模板方法 | 固定骨架、子类填步骤 | 依赖继承，策略只能编译期绑定；无法按活动的 `policyType` 在运行期切换 | 否决 |
| **策略模式** | 运行期可换；服务只依赖接口；新增方式零改核心流程 | 多 4 个类（接口 + 2 实现 + 工厂） | **采用** |

**结论与理由**
`RegistrationPolicy.decide(ctx)` 只回答「这次提交进入哪个状态」，是纯函数式决策、无副作用；`PolicyFactory` 按 `activity.policyType` 选实现。
新增「候补队列」只需新增 `WaitlistPolicy` 并在工厂注册，`RegistrationService` 不动。

**代价**：类数量 +4；调用链多一次工厂间接；调试时要先看工厂选了哪个实现。

**失效信号**
- 策略接口出现第 2 个方法（说明职责开始膨胀，可能该拆）；
- 服务层出现 `instanceof` / 类型判断（说明抽象泄漏）；
- 新增方式时需要改 `RegistrationService`（说明 OCP 已破）。

### D2 报名与通知解耦 → 采用观察者（事件总线）

**背景**：报名/审批成功后要写站内消息。指导书要求「通知失败不得导致报名记录无声消失」，且「避免重复通知」。

**候选对比**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 服务内直接写消息表 | 最简单、事务天然一致 | 报名事务被通知拖死：消息写失败就整体回滚；新增渠道要改报名服务 | 否决 |
| 消息队列 | 天然削峰、可重放 | 需额外中间件；指导书明确「无须引入消息队列」；2 周工期不划算 | 否决 |
| 同步事件总线（进程内） | 零依赖；可插拔订阅者；失败可隔离 | 无持久化队列，进程崩溃会丢事件（本项目用「事件先落库 + 失败留痕」兜底） | **采用** |
| 数据库触发器 | 与业务同库，天然持久 | 逻辑藏在 DB，难测试、难版本化 | 否决 |

**结论与理由**
`RegistrationService` 在事务提交后 `EventBus.publish(RegistrationEvent)`；`InboxNotifier` 作为订阅者写 `messages`。
失败时写 `notify_failures(event_id, payload, error)`，不回滚报名（BR6 的事务边界即在此）。

**幂等**：`event_id = registration_id + 目标状态 + 版本`；`messages(registration_id, status)` 唯一索引兜底；订阅者按 `event_id` 去重。

**代价**：多一层间接（调试需追事件链）；事件与业务不同库表时存在「已发布未消费」窗口（本项目同库同进程，窗口极小）。

**失效信号**
- 出现「报名成功但一直没消息」且 `notify_failures` 无记录（说明事件没发出去）；
- 同一条报名出现两条相同状态的消息（幂等失效）；
- 订阅者开始反向调用报名服务（循环依赖）。

---

### D3 持久化隔离 → 采用 Repository 接口

**背景**：需要持久化活动、报名、消息；同时希望业务逻辑可单测（不启数据库）。

**候选对比**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 服务内直接写 SQL | 代码最短 | 业务与 SQL 缠死；单测必须建库；换存储要改业务 | 否决 |
| ORM | 开发快 | 需第三方库（违反零依赖约束）；隐式行为多 | 否决 |
| **Repository 接口 + SQLite 实现** | 业务只依赖接口；可用内存实现做单测；换存储只改装配 | 多 5 个接口 + 1 个实现类（约 +150 行） | **采用** |

**结论与理由**：`app.py` 负责组装（依赖注入），业务代码不 `import sqlite3`。

**代价**：接口样板代码；查询稍复杂时要在仓储里加方法（而不是随手写 SQL）。

**失效信号**：仓储接口方法数快速膨胀（说明聚合边界没划好）；服务层出现 `sqlite3` 或 SQL 字符串。

### D4 名额规则归属 → 放在服务层（公共规则）

**背景**：名额上限是两类报名方式共同面对的不变量；指导书要求说明「名额检查属于公共规则还是策略责任」。

**候选对比**

| 方案 | 问题 |
|---|---|
| 放进策略 | 审核型「提交时」不占名额、批准时才检查，会把同一条规则写两遍，且策略要读活动聚合状态，职责越界 |
| 放进 Activity 实体 | 需要知道「已通过数」，实体要么持有全部报名（聚合过大），要么依赖仓储（污染领域层） |
| **放进 RegistrationService** | 一处实现、两处调用（提交与批准），用 `countApproved` 取数，规则可单测 |

**结论与理由**：名额是**活动聚合的不变量**，由应用服务在编排时校验；策略只做「通过/待审核」的决策。
对应时序图：`seq-register-direct`（提交时）、`seq-approve`（批准时再查一次）。

**代价**：服务层多一次计数查询（可用索引覆盖，成本可忽略）。

**失效信号**：未来若允许「超卖比例」「候补自动补位」，这条规则会变复杂——此时应考虑把它抽成独立 `CapacityPolicy`，但**不是现在**（YAGNI）。

### D5 删除有报名的活动 → 软删除

**背景**：BR7 允许「拒绝删除并提示」或「软删除」，需要二选一并说明。

**对比**

| 方案 | 后果 |
|---|---|
| 硬删除 + 级联删报名 | 历史消息与统计断裂；审计不可追溯；违反「已发生业务事实不消失」 |
| 拒绝删除并提示 | 数据最安全，但管理员无法下架误建活动，运维体验差 |
| **软删除（`deleted_at`）** | 列表/详情不可见、不可报名；历史报名与消息保留；可恢复 |

**结论与理由**：选软删除。代价是每个查询都要带 `deleted_at IS NULL`（在仓储层统一加），以及需要定期归档（本项目不做）。

**失效信号**：出现「重复活动」投诉（说明缺合并/恢复入口）；查询漏加过滤条件导致已删除活动被报名。

---

### D6 前端形态 → Vue3 + Vite（构建产物由后端托管）

**背景**：需要学生端与管理端页面；环境可装 Node；部署目标是单台 Linux 云主机。

**对比**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 服务端渲染 HTML | 零构建、部署最简单 | 交互（筛选、状态刷新、消息角标）要整页刷新，演示观感差 |
| 纯 JSON API + 无前端 | 最省事 | 指导书要求「学生浏览活动并报名」，需要可演示界面 |
| **Vue3 + Vite** | 组件化、开发热更新、构建后是纯静态文件 | 引入 Node 工具链；构建产物需与后端一起部署 |

**结论与理由**：Vue3 + Vite（JavaScript，不用 TS 以控制工期）。开发期 `vite dev` 用 proxy 转发 `/api` 到 8000；生产期 `npm run build` 产出 `dist/`，由后端 `StaticHandler` 托管，实现**单进程单端口**部署。

**代价**：多一套 `node_modules`（约 200 MB，不入库）；部署时需先构建。

**失效信号**：构建产物与后端版本不一致（应把 `dist` 纳入发布脚本）；开发期跨域配置泄漏到生产。

## 3. 被否决方案汇总

| 方案 | 一句话否决理由 |
|---|---|
| 单例 + 全局状态 | 与依赖注入冲突，测试难隔离 |
| 状态模式管理报名状态 | 状态迁移简单（4 态），上状态机会让代码比问题复杂 |
| 消息队列 | 指导书明确不要求，2 周工期与单机部署不匹配 |
| ORM | 违反零第三方依赖约束 |
| 数据库触发器发通知 | 逻辑不可测、不可版本化 |

## 5. 设计风险登记（可能被 CR 打穿的地方）

| 风险 | 触发条件 | 影响 | 预案 |
|---|---|---|---|
| R1 名额规则变复杂 | CR 引入候补队列/超卖比例 | D4 的「服务层一处实现」会膨胀 | 抽出 `CapacityPolicy`，服务层改为调用 |
| R2 新增报名方式需外部数据 | CR 要求「按学院限额」 | 策略需要额外入参，`decide(ctx)` 签名要扩展 | 扩展 `RegistrationContext`（新增字段，不破坏现有实现） |
| R3 通知需多渠道路由 | CR 要求按活动类型选渠道 | 订阅者增多，事件总线需要路由能力 | 在 `InboxNotifier` 前加一层 `ChannelRouter` |
| R4 活动状态语义扩展 | CR 引入「已结束/已取消」 | `Activity.isOpen` 判断需细化 | 引入 `ActivityStatus` 枚举，替换布尔判断 |
| R5 审批需要批量操作 | CR 要求批量批准 | 服务层出现循环调用，事务边界要调整 | 新增 `approveBatch`，内部复用单条逻辑，事务包在外层 |

## 6. 变更演练预案（用于预判 CR 的修改范围）

假设教师 CR 为「**新增候补队列：满员后报名进入候补，有人取消时自动补位**」，按当前设计的预期改动：

| 层次 | 预期改动 | 是否改核心业务类 |
|---|---|---|
| 数据库 | 新增 `waitlist_pos` 字段或 `status='WAITLISTED'` | 否（迁移脚本） |
| 领域 | `Registration` 增加状态与排序语义 | **是** |
| 策略 | 新增 `WaitlistPolicy` | 否（新增） |
| 服务 | 取消报名后触发补位；名额规则扩展 | **是** |
| 通知 | 新增「已补位」事件与文案 | 否（新增订阅逻辑） |
| 前端 | 我的报名增加候补状态展示 | 否 |

结论：预计「修改的核心业务类」为 2（`Registration`、`RegistrationService`），这是 D4「名额规则集中在服务层」的收益；若当初把名额分散到策略，此处需改 3–4 个类。

## 7. 结论

- 六个决策点的共同取向：**把「会变的东西」隔离到可替换的单元**（策略、订阅者、仓储），把「不变量」集中在服务层。
- 明确承认代价：类数量与间接层增加，换来变更时的修改面收敛。
- 第 2 周将用 §4 的口径给出客观数字，并与 §6 的预期对照，验证或推翻本节结论。
